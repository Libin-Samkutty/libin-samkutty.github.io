A check is worth only the independence between it and the thing it checks. Share a module, a model, a tokeniser or a config resolver, and a whole class of defect becomes invisible to it: not unlikely, invisible. The check will keep passing, confidently, for exactly as long as the defect exists.

## The clearest case: a model judging its own family

The first LLM-as-a-judge I built used the same model family as the generator it was grading. It looked reasonable. Its verdicts were fluent and its reasoning read well.

It isn't an independent check. It's closer to a mirror.

The judge shared the generator's language preferences and the generator's failure modes, so it consistently found the generator's output reasonable. Obvious failures still surfaced. A truncated answer is a truncated answer to anybody. The subtle quality drops, the ones that actually matter, stayed invisible, because the judge would have made the same mistake for the same reason.

The redesign was four constraints: a judge from a different model family, binary verdicts instead of a floating score, a human-annotated calibration set, and temperature zero. On the tone criterion, the result was {% metric "judge_agreement_geval" %}.

The structural version of that fix now runs across the whole evaluation stack: the retrieval-metrics judge, the criteria judge, and the generator sit on three distinct model families. Not because any one of them is best, but because a regression one of them is blind to is unlikely to be invisible to all three.

## The same argument without an LLM anywhere in it

Judge independence gets discussed as though it were a quirk of evaluating language models. It isn't. It is one instance of a rule about checkers in general.

A validation script that imports the production normaliser cannot catch a normalisation bug. It will normalise the input wrongly in precisely the same way, then confirm that the wrong result matches the wrong expectation, and report success.

A snapshot baseline generated by the pipeline it guards cannot catch a defect that existed at the moment the baseline was recorded. Snapshots detect change, and a bug present at recording time is not a change. This is fine as long as everyone knows it: the failure is mistaking stability for correctness.

A fixture built by recording a live response reproduces that response, not the contract behind it. It will keep passing after the provider changes a field that the recording happens not to exercise.

Config resolution deserves its own mention because it is the sneakiest of the four. If your test resolves the environment, the feature flag or the timezone through the same code path as the application, then every configuration bug is a bug your tests are guaranteed to agree with.

## A worked example: a dependency bump moved the boundary

The semantic cache regression suite holds a set of known-equivalent phrase pairs, chosen by hand, asserted to hit the cache. They had been asserted for months and had never been interesting.

Then an embedding library was upgraded: a minor version, a routine container rebuild, no application code touched. The newer model tokenised a medical abbreviation into different subwords. That shifted the embeddings enough to push several of those known-equivalent pairs from just above the similarity threshold to just below. The suite went red on a dependency bump.

The fix was straightforward once seen: regenerate the vector index with the new model before deploying, rather than after. Without the suite, the rollout would have silently cut the cache hit rate and raised model call volume and latency for one market, and the first person to notice would have been reading a cost report weeks later.

What made that catch possible is worth being precise about. The independence there is not a model or a module. **It is that the expected value was written down by a human at a point in time and never recomputed from the system under test.** Had the suite computed expected similarity with the same embedding model at run time (the natural, tidy, don't-repeat-yourself thing to do), every pair would still have "matched" after the upgrade, because both sides of the comparison would have moved together. The suite would have been green and the cache would have been degraded.

## Where I chose duplication on purpose

The cache validation harness reimplements production's input normalisation rather than importing it. That is duplication, and duplication has a real cost: the two can drift, and when they drift the harness reports a failure that is its own fault.

I took that trade knowingly, because a false failure is loud and a shared bug is silent, and I would rather spend an hour a quarter on a false alarm than ship a normalisation bug that my checker agreed with. **In a checker specifically, loud duplication is safer than silent reuse.** That rule does not generalise to application code, which is exactly why it needs stating out loud: otherwise a reviewer applies the usual instinct and refactors the independence away in the name of tidiness.

## An audit you can run this week

Go through your own suite and ask, per check:

- Does the assertion import the function that produced the value? Watch for config resolution, date and timezone maths, currency rounding, slug generation, text normalisation.
- Was the expected value generated by the system under test? If so, did a human read it before it became a baseline?
- Does the judge, model or embedding share a family with the thing it is judging?
- Does the mock reproduce the provider's happy-path response, or the provider's contract including the ways it fails?

Then ask the sharp version of all four: **what would this check do if the shared dependency were wrong?**

Answer honestly for each one. Some answers will be "pass, silently". Those are the checks to redesign. Or to keep knowingly, paired with a second check somewhere that shares nothing with the first.

## What independence costs

It is not free and I am not pretending otherwise. An independent judge is a second model to pay for, calibrate and keep calibrated. Hand-recorded expectations go stale and need someone to own them. Duplicated logic drifts and produces false alarms. Contract tests are more work than recorded fixtures.

The goal is not to make every check independent. It is to know which of your checks are mirrors, and to stop counting them twice when you reason about coverage. A suite of two hundred tests where sixty share the defect surface of the code they test has the coverage of a hundred and forty. That is a survivable number. Believing it is two hundred is not.

## The rule

Every check inherits the blind spots of everything it shares with the thing it checks. Write down what the two share. That list is the exact set of defects the check cannot find.
